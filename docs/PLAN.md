## Context

You want one remote-desktop tool that needs only SSH. Sunshine/Moonlight needs a PIN pairing on every workstation. Gliff (omacom/gliff, MIT, Rust, v0.4.3) is the tool you like, but its server only works on Hyprland. You want to:

1. fork Gliff,
2. keep its Hyprland support as upstream has it,
3. add a GNOME backend, written in Rust,
4. keep the fork in sync with upstream,
5. then drop Sunshine and Moonlight from vexos.

This plan covers the fork, the GNOME backend, how we keep in sync, and the vexos changes.

## How it would work, in plain language

Gliff has two programs. The **viewer** (`gliff`) is the window you look at. The **server** (`gliff-server`) runs on the machine being controlled. SSH starts the server and carries everything, so there are no open ports and no pairing.

The server has five jobs:

- grab pictures of the screen
- squeeze them into video (the GPU encoder, which is the clever part)
- send your keyboard and mouse into the desktop
- share the clipboard
- (optional) make a private extra screen that matches your window

The wire protocol carries only keycodes, pointer moves, clipboard data and video. It never mentions Hyprland. The video code never mentions Hyprland. **Only the "talk to the desktop" part does**: grab screen, inject input, bridge clipboard, create and resize the private screen, keep the screen awake.

So the project is: **give the server a second way to talk to the desktop, this time to GNOME.** Everything else is reused.

**One correction found later:** the viewer is not completely free of Hyprland either. `crates/gliff/Cargo.toml` depends on `hypr-capture`, `hypr-ipc` and `hypr-input`, and `net.rs` calls `hypr_capture::render_node`. My guess is the viewer uses them to find the GPU and to read the local keyboard layout (`hypr-input` exports `watch_keymap` and `keymap_from_names`), but I have **not** read that code. So the seam also covers a small viewer-side part: local keyboard layout detection and GPU selection on a GNOME machine.

On GNOME the "talk to the desktop" part maps almost one-to-one onto GNOME's own remote-desktop interface (Mutter). I checked these interfaces in Mutter's published D-Bus files:

| Server job | Hyprland today | GNOME (Mutter D-Bus) |
|---|---|---|
| Grab a monitor | `ext-image-copy-capture` | `ScreenCast.RecordMonitor`, delivered as a PipeWire video stream |
| Private screen | `hyprctl output create headless` | `ScreenCast.RecordVirtual` (a virtual monitor) |
| Cursor shape and position | capture events | `cursor-mode = 2` (cursor sent as stream metadata) |
| Keys, mouse, scroll | virtual keyboard/pointer protocols | `NotifyKeyboardKeycode`, `NotifyPointerMotionAbsolute`, `NotifyPointerButton`, `NotifyPointerAxis`, `SetKeymap` |
| Clipboard | `ext-data-control` | `EnableClipboard`, `SetSelection`, `SelectionRead`, `SelectionWrite` |
| Find the session | Hyprland socket | the user's session D-Bus at `/run/user/<uid>/bus` |

Gliff's own input commands use evdev keycodes and absolute pointer positions. Mutter accepts exactly those.

### How we keep it in sync with upstream

You asked for a separate "GNOME branch". I recommend a small change to that idea. **One fork, one main branch, two backends in the same code, chosen at runtime** (GNOME or Hyprland, detected from the running session). A long-lived separate GNOME branch would drift, and every upstream change would need hand-merging into it.

- `upstream` branch: an exact copy of omacom/gliff, fast-forward only. A weekly job updates it.
- `main`: upstream plus **our additions**. The additions are new crates plus one small "seam" change.
- The **seam**: Gliff's server calls Hyprland directly in about 8 places in `crates/gliff-server/src/session.rs` (77 KB) and `main.rs`. We replace those calls with a small `Backend` interface. This is the only edit to upstream files that matters. It is where nearly all merge conflicts will happen, so we keep it as small as possible (see "Upstream sync" in the log below for what it came to).
- The GNOME code lives in **new crates** (`gnome-ipc`, `gnome-capture`, `gnome-input`, `gnome-clipboard`) that upstream never touches, so those never conflict.
- Every week a CI job merges `upstream` into `main`, builds, runs the tests, and opens a pull request for you to approve. It labels the PR **"needs GNOME mirror"** if upstream changed the Hyprland-only crates (`hypr-*`) or the session code. Those are the changes that need a matching change in the GNOME crates. Changes to video, viewer or clipboard flow mostly flow automatically, but a protocol or server change can still need GNOME work, which is why the label goes on any change to those crates too.
- **First step upstream:** before writing any code, open an issue upstream saying "we'd like to add a compositor backend interface and a GNOME backend". If they accept the seam, our fork shrinks to just the GNOME crates and the sync problem mostly disappears. If not, we carry the small seam patch ourselves.

## Verified facts vs unverified

Verified by reading sources this session:
- Gliff's wire messages (`gliff-proto/src/msg.rs`): no Hyprland content. Keys are evdev keycodes. Pointer motion is absolute.
- Capture API (`hypr-capture`): frames carry `DmabufInfo` (fd, fourcc, modifier, planes) or a wl_shm memfd, plus damage. `CaptureMode::Shm` already exists and forces the CPU path.
- Hyprland coupling in `session.rs` is listed above. Clipboard bridge and transfer logic are generic once started.
- Mutter's D-Bus interface files list every method in the table above, and they document **no authentication**. They also say the API is "private and not intended to be used outside of the integrated system", with "no compatibility between versions".
- Mutter's `CreateSession` code in `meta-remote-desktop.c` has no caller check. gnome-shell issue #3943 proposes an allow-list but records no decision.
- Upstream Gliff has no issues or PRs mentioning GNOME, KDE or a backend interface. There is no CONTRIBUTING file. It has 325 commits, 27 open issues and 39 open PRs.

- Step 1 (an hour): try the existing Linux viewer under WSL2/WSLg with CPU decode (`--video cpu`). Untested; shortcut capture in WSLg may be poor.

## Difficulties and how we handle them

1. **Mutter's API is private and may change between GNOME releases.** NixOS pins the GNOME version, so we only face a change when we update. We cover it with a NixOS VM test that boots GNOME and runs the probe, so a nixpkgs bump that breaks it is caught before you switch. We keep the portal route (via the `ashpd` crate) as a second choice the server can pick at runtime.
2. **Unattended permission.** M0 answers this first. See the gate.
3. **PipeWire dmabuf negotiation.** Getting zero-copy video from PipeWire into Vulkan needs the right modifiers per GPU. We start with shared memory (slower, works everywhere, Gliff already has this CPU path) and add dmabuf per GPU once correct. NVIDIA already needs shared memory in upstream for capture, so that is no regression.
4. **Frame timing.** Gliff asks for a frame when it wants one. PipeWire pushes frames. We keep only the newest frame, drop older ones, and re-send the last frame on a keyframe request. Mutter only sends frames when the screen changes.
5. **Keyboard layouts.** The client sends its keymap and the server applies it. Mutter's `SetKeymap` has to be tested for that. Fallback: send keysyms or rely on matching layouts.
6. **Locked screen and sleeping displays.** Hyprland uses screen-power control. GNOME needs an idle inhibit, and capture while locked is unverified (M0).
7. **Password prompts.** You use password SSH. The viewer is a GUI app, so ssh can't prompt in a terminal. We test what happens, then fix it with an askpass helper or the key route. We never turn off password login.
8. **Upstream drift.** Mitigated by the small seam, the weekly merge PR, the label, and the upstream issue. Honest cost: someone has to look at one PR a week, and some upstream changes will need a GNOME-side change by hand.
9. **Upstream lock-in and effort.** Realistic size: a few days for M0, then weeks for M3 and M4. A fork you maintain indefinitely. Sunshine stays in vexos until M4 passes, so you are never left without remote access.
10. **Licence.** Gliff is MIT. Keep its LICENSE and NOTICE (it bundles OpenH264, BSD-2). Our GNOME crates are ours. Using Mutter's D-Bus API does not make our code GPL.

## Decisions and results log

### M0 result (2026-11-15) — spike run on a vexos desktop VM (GNOME Shell 50.6, software rendering)

- Over SSH, with nobody at the machine: RemoteDesktop + ScreenCast sessions, `RecordMonitor` and `RecordVirtual` (shared-memory frames with real pixels), and the clipboard (two sessions, both directions) all worked with no prompt reaching the caller.
- Key, pointer and scroll calls were accepted; their effect on the desktop was not observed. Cursor metadata never arrived (no cursor meta block on any buffer), so absolute-pointer behaviour is unconfirmed.
- **Locked screen: blocked.** After `loginctl lock-session` the open session was closed in 3.3 s and a new one failed with `Session creation inhibited`; it worked again after `loginctl unlock-session`. This matches Mutter/GNOME Shell source (`unlock-dialog` mode does not allow screencast, so Shell calls `inhibit_remote_access()`).
- `SetKeymap` is untrusted: the run that called it coincided with a GNOME Shell SIGSEGV in the capture path (llvmpipe texture allocation); three later runs without it did not crash. `KeymapCapabilities` reads back empty on this Mutter. The keysym or matching-layout fallback is needed.
- Not tested: dmabuf, real GPUs (AMD/Intel/NVIDIA), an idle-triggered lock, the login screen, reading what a desktop app copied.

### Decision (2026-11-15)

This fork **replaces Sunshine/Moonlight**. The cost is accepted: a locked workstation cannot be reached with this backend. Sunshine stays in vexos until M4 passes, as planned.

### M3 step 1 result: `gnome-ipc` (2026-11-17)

- New crate `crates/gnome-ipc` (zbus blocking API, no async runtime needed). `discover` finds the user's active local graphical session from an ssh login with `loginctl` (skips our own remote login and greeter sessions) and builds the session bus address. `mutter` connects to the bus, reads both Mutter `Version` properties, lists monitors (`DisplayConfig.GetCurrentState`) and wraps a linked RemoteDesktop + ScreenCast `Session` (`record` a monitor or a virtual monitor, `start`, wait for the PipeWire node, `stop`). Each `Session` has its own bus connection and closes it on drop, so Mutter ends the session even when a listener thread is still blocked. Probe binary: `gliff-gnome-probe [--virtual]`.
- Verified on the GNOME 50.6 VM over ssh (`nimda@192.168.100.71`), with no `DBUS_SESSION_BUS_ADDRESS` or `XDG_RUNTIME_DIR` set: session found, Mutter RemoteDesktop v1 and ScreenCast v4, monitor and virtual capture both reach a PipeWire node, repeated runs leave no sessions behind, a bad bus address fails with a clear message. A temporary check (deleted) showed that a failed `RecordMonitor`, an unstarted session and a fresh session all release their listener threads once dropped. `scripts/check.sh` passes; the crate has 8 unit tests.
- Not verified: locked screen (known limit), a failed `Start`, more than one monitor, anything about frames (step 2).
- Review: two rounds with Sol (`gpt-6.1-sol`, default effort). Round 1: one `should` (listener threads kept the connection alive on failed create or start, and Mutter rejects `Stop` before `Start`); fixed with a connection-closing guard. Round 2: approved, nothing open. Sol could not run cargo in its sandbox, so every test result above is from this machine.

### M3 step 2a result: `gnome-capture`, shared-memory frames (2026-11-17)

- New crate `crates/gnome-capture`: `Capturer::start(Options, sink)` connects to the PipeWire node `gnome-ipc` opened (over the socket in the user's runtime dir, no environment variable needed) and emits the same `CaptureEvent`s as the Hyprland capturer. `request_frame`, `recapture` and drop match the pull model `gliff-server` uses; PipeWire pushes, so `pacer.rs` keeps the newest frame, replaces an unsent one, and can send the last frame again. Frames are copied into a ring of memfd buffers (the `buffers` the consumer may hold, plus one for re-sends), so PipeWire buffers go back at once. `cursor.rs` turns cursor metadata into `CursorShape` and `CursorPos` events. Probe: `gliff-gnome-capture-probe [--virtual] [--connector NAME] [--cursor hidden|embedded|metadata] [--png FILE] [--secs N]`.
- Upstream edit (approved): two lines in `crates/hypr-capture/src/lib.rs` plus the new file `external.rs`; see the footprint table. `nix/package.nix` (ours) gained `pipewire` and the bindgen hook.
- Verified on the GNOME 50.6 VM (software rendering): a monitor capture gives a correct 1920x1080 frame (the saved PNG was the real desktop, colours and orientation right), first frame in 150 to 350 ms, recapture re-sends the last frame, a virtual monitor works (the format renegotiated once, so two `Ready` events), `--cursor embedded` and `hidden` work. Cursor shape (24x24) and position now arrive in `metadata` mode. This resolves the M0 gap, whose likely cause was asking for the metadata with a fixed size instead of a size range. `scripts/check.sh` passes (12 unit tests in the crate) and `nix build path:.` passed.
- Bug found while testing: a frame request made before the format was negotiated was lost when the ring was built; fixed with a test.
- Not verified: dmabuf (2b), a moving or hiding cursor live (needs input, step 3; covered by unit tests and Sol's reading of Mutter's source only), a real GPU, mid-capture resize beyond the one virtual renegotiation, a slow consumer under load, PipeWire stream-error paths.
- **Idle blanking blocks capture even with screen lock off.** On the VM (idle delay 300 s, `lock-enabled` false), after five idle minutes `org.gnome.ScreenSaver.GetActive` was true and Mutter refused sessions with "Session creation inhibited". `org.gnome.ScreenSaver.SetActive(false)` over ssh cleared it and capture worked again. With screen lock enabled this would probably show a password prompt instead (not tested). Consequence for step 5: wake the screen before creating a session and inhibit idle while one runs. ### M3 step 4 result: `gnome-clipboard` (2026-11-17)

### M3 step 2b findings: what Mutter offers on NVIDIA, and the plan (2026-11-19)

Discovery only; no code changed. Run over ssh on the NVIDIA desktop (RTX 2080 Ti, driver 595.71.05) with the packaged `gliff-gnome-capture-probe` (capture of `HDMI-1`, 1920x1080) and `pw-dump` while it ran, which prints the formats Mutter's stream node offers.

- **Mutter offers dmabuf on NVIDIA, with tiled modifiers only.** For both `BGRx` and `BGRA` it lists 13 NVIDIA block-linear modifiers (`0x0300000000606010` to `...15` and `0x0300000000e08010` to `...15`) plus the implicit modifier (`0xffffffffffffff`, "invalid"). **Linear (`0`) is not offered**, so the CPU cannot map these buffers. After that comes the same two formats again with no modifier at all, which are the shared-memory (memfd) form we use today. Size and frame rate are fixed by the monitor (1920x1080, up to 60 fps).
- Our consumer today offers no modifier, so Mutter gives it shared memory. That is why the GNOME backend is on the CPU pipeline (see "M3 wiring result").
- **What the GPU encoder already does with such a buffer:** `gliff-vk` imports a single-plane dmabuf with an explicit modifier and a stride (`Image::import_dmabuf`), the same call the Hyprland path uses for NVIDIA's tiled buffers. So the encoder side needs no change; only capture has to hand it a `CaptureBuffer` with a real dmabuf fd, modifier and stride.
- **Not checked:** whether Vulkan on this card accepts each of those modifiers (needs the code below to ask), and whether the picture is complete when read (Mutter may still be drawing into a buffer when we get it; see risks).

**Plan for 2b, in pieces, each ending at a gate with a probe on the NVIDIA desktop:**

1. **Negotiate.** For each pixel format `gnome-capture` offers two alternatives, as PipeWire's dmabuf rules describe: one with a modifier list (flags MANDATORY and DONT_FIXATE) and one without (memfd, as now). The list is what Vulkan on the render node can import for that format (single memory plane, sampled). The buffers parameter asks for `SPA_DATA_DmaBuf` only when the result carries a modifier; otherwise for memfd as now. Who fixes the modifier: Sol's review said Mutter does and the consumer only reads the result; my first note said the consumer answers a second round. **Measured: Mutter hands the choice back (`MODIFIER_FIXATION_REQUIRED`) and the consumer fixes it** (see "M3 step 2b result, part 1"); the code handles both.
2. **Hold, do not copy.** With dmabuf the PipeWire buffer is kept, not copied to a memfd. PipeWire's `add_buffer` and `remove_buffer` callbacks say which buffers exist; each gets a stable ring index while its pool lives, and a fresh generation (so a fresh `gliff-vk` import-cache key) whenever the pool is replaced, for example on a resize or a renegotiation. A file descriptor number is not an identity, since numbers get reused. The pacer already decides which slot is free, pending, in flight or kept for a re-send; a PipeWire buffer goes back to Mutter only when its slot is free, and a buffer that was pending and replaced by a newer one goes back at once. A re-send must not point at a buffer that has already been returned. A release carrying an old generation must not re-queue a buffer that was removed. The pool must hold the frames the server may keep, one for re-sends, and some for Mutter to draw into, so the request asks for more buffers than the 3 + 1 of the shared-memory ring.
3. **The `process` path.** Today it rejects a buffer whose chunk size is 0 and requires a CPU mapping (`data.data()`). A valid dmabuf may have chunk size 0 and cannot be mapped. The path branches on the data type first: dmabuf takes its fd, offset and stride without either check; cursor metadata is read the same way for both, and a buffer that carries only a cursor update goes straight back.
4. **A buffer type for them.** `CaptureBuffer` has two kinds of backing today (a GBM object and a memfd), both private to `hypr-capture`. A dmabuf from PipeWire needs a third. This is an upstream edit; see below.
5. **Policy reaches the capturer.** Today the GNOME backend ignores the capture config's `mode`, `render_node` and `shm_fallback`, and a virtual output's capture is started in `create_virtual_output`, before the server's `start_capture` only attaches its sink. So the plan: the config is passed to the capturer on both paths. For a virtual output, `start_capture` applies it to the capturer that already runs, and a session that needs shared memory (CPU pipeline, `--capture shm`) switches it before any frame is replayed to that session (buffered dmabuf frames are dropped, since the CPU cannot map them). The choice survives a resize. `GnomeBackend::forced_capture_mode` then stops forcing the CPU pipeline, and `use_shm` becomes real (renegotiate to the memfd form), so the server's "first GPU encode failed, fall back to CPU" path (`session.rs`) works on GNOME as on Hyprland.

**Upstream edits this needs (not made; to be approved first):**
- `crates/hypr-capture/src/lib.rs`: one more variant of the private `Backing` enum, and its arms in `with_mapped` and `read_bgra` (about 10 lines, additive). Alternative without the edit: import the fd into a GBM buffer object on the render node, so the existing GBM variant is used; this adds a `gbm` dependency and may not work for NVIDIA's tiled buffers, so it is the worse choice.
- `crates/gliff-vk/src/device.rs`: one public function that lists the modifiers the device can import for a DRM format (about 20 lines, built from `modifier_properties`, which is crate-private today). Alternative without the edit: `gnome-capture` asks Vulkan itself with `ash` (about 80 lines of our own, plus finding the right device from the render node).

**Risks (all unverified):**
- **Sync.** Mutter draws into the buffer on the GPU; the buffer may be handed over before that finishes. If NVIDIA's implicit sync does not cover it, frames could show a half-drawn picture. The first probe must compare a GPU readback with the shared-memory frame.
- **Another GPU.** On a laptop with two GPUs, Mutter renders on one and the render node we encode on may be the other (a dmabuf may not import across them). The server's fallback to the CPU pipeline on a failed first encode covers this; it must be tested on the laptop (read-only checks only there).
- **No dmabuf at all** (the VM's software renderer, some remote setups): Mutter then offers only the memfd form, which we already take.
- **Nothing changes for the viewer.** This only moves the encode from the CPU to the GPU; it should be faster and lighter on the host, with the same picture.

### Keyboard layouts on GNOME (2026-11-19)

The viewer's keyboard layout now reaches the keys on GNOME when it differs from the server's (`SetKeymap` was refused before, so a viewer on another layout than the server typed the wrong characters). The plan's own fallback, keysyms, is what works: Mutter has no keymap upload for RemoteDesktop sessions, but `NotifyKeyboardKeysym` takes a keysym and Mutter finds the key for it and presses the Shift it needs (levels 1 and 2 only; Sol read `meta-virtual-input-device-native.c` for that).

- **Design** (all in `gnome-input`, `gnome-ipc` and `gnome-backend`; no upstream file touched). The server's own keymap is read from its compositor (`hypr_input::watch_keymap`, the code the viewer uses for its own keymap, pointed at the desktop's Wayland socket; `ServerKeymap`, followed by `GnomeBackend`). Per viewer layout: **if it gives every key the same symbols on every level as the server's (first layout), the server's layout is not known, or the server has several layouts (which one is active is not known here; **superseded 2026-11-22**: such a server now gets key codes only when the viewer's layout is one of its layouts, see "Several layouts on the server"), keys go as key codes exactly as before** (so a viewer on the server's layout loses nothing: every level, dead key and media key is the server's own); otherwise `ViewerKeys` (xkbcommon, `keymap.rs`) keeps the viewer's key state and every key becomes the keysym the viewer's layout gives it, remembered so the release matches. In that mode lock keys and AltGr stay local, and so does Shift (Mutter adds the Shift a character needs, and a forwarded Shift applied twice typed `!` for a French Shift+1 on the first hardware run); Shift goes to the server only before a key that is not a character, a pointer button or a scroll step (or when pressed with a button held), is let go before the next character, and is released when the viewer's last Shift is. Control, Alt and Super go as themselves. Keypad keys go as the plain keys (Mutter makes `KP_1` a shifted key, which Num Lock turns into End, and `KP_Left` is Left only with the server's Num Lock off: digits go as characters, navigation as Home/Left/Up/…/Delete), and the keypad starts with the server's Num Lock state. Only one character key is down on the server at a time, and it is let go before any key that is not a character and before a pointer button or scroll (the Shift Mutter made for an upper-case letter goes with it, so it cannot turn Left into Shift+Left or a click into Shift+click). A key the layout has no symbol for goes as its code; a new layout, or a change of the server's, lets go of what was held first (and those releases are sent even if the command that triggered them fails). Before any layout arrives keys go as codes.
- **Sol, round 1** (seven findings, all taken): S1 keypad digits with Num Lock became End (fixed by sending the plain character; and same-layout viewers no longer use keysyms at all), S2 a Shift forwarded for Shift+Left shifted the next character (the server's Shift is let go before a character), S3 Shift released while an upper-case letter was held left Mutter's Shift on for the next key (one character key at a time), S4 level-3 symbols of the server's own layout could not be sent as keysyms (same-layout viewers use key codes; a different layout cannot type what Mutter cannot, see below), S5 Shift+scroll and S6 Shift pressed during a drag lost Shift (both now reach the server), S7 repeated presses were counted twice by xkb (state is updated on the first press only). The code first used keysyms for every viewer layout; the rule above came from S1 and S4.
- **Sol, round 2** (CHANGES; four taken): S1 keypad navigation depended on the server's Num Lock (`KP_Left` is Left only with it off; now normalised to the plain navigation keys, and `KP_Enter`, `KP_Tab`, `KP_Space` and `KP_F1`..`F4` likewise), S3 a character key still held leaked Mutter's Shift into navigation keys and pointer events (it is let go first), S8 the releases for a mode change were lost if the command that carried them failed (`Input::send` applies them anyway, then returns the error), S9 a server with several layouts was compared on its first layout only (now stays on key codes). Each has a unit test except S8, which sits in `Input::send` and needs a live session.
- **Sol, round 3** (CHANGES; both taken, and the round limit is reached, so these two fixes were checked by unit tests only): Shift+Tab sent `ISO_Left_Tab`, for which Mutter adds a Shift of its own that outlived the viewer's Shift and made the next letter upper case (now plain Tab with the explicit Shift), and a held dead key (`dead_diaeresis` from US International on a French server) bypassed the one-character-key rule because it has no UTF-32 value (dead keysyms are now character keys, let go before the next one). The four round-2 fixes were judged correct.
- **Probe `gliff-gnome-layout-probe`** (crate `gnome-input`, packaged): a fullscreen test window with a text field, clicks into it with injected input and types 15 scenarios under the `us`, `de`, `fr` and `ru` layouts, comparing the field's text. ### A changing screen and a client that stops reading, on GNOME (2026-11-24)

Every run so far captured a static screen, and no test had a client that stops reading. New: `gliff-gnome-animate [SECS [RECTS]]` (crate `gnome-input`, packaged) is a fullscreen window that changes every frame (300 coloured rectangles and a sweeping bar by default), and `serve_probe --load SECS [--stall SECS]` (on a mirrored screen; with `--headless` too, later, see below) reads the stream for SECS seconds and reports frames per second (also by ten seconds), bytes a frame, the longest gap, key frames, the server's CPU and memory; it fails below 20 frames a second or on a gap of a second. With `--stall` the client then stops reading and acknowledging for that long, and the probe checks that the server's memory, sampled every two seconds, stays within 100 MB, that a frame comes within 3 s of reading again, and that the first two seconds are not a replay of the stall (at most 240 frames). The gaps it reports include the wait for the first frame and the silence after the last; each read has a 5 s limit; the CPU time uses the system's clock-tick rate.

- **Result on the NVIDIA desktop, before the frame-rate fix below** (GNOME 50.6, packaged `gliff-server`, mirroring `HDMI-1` while the animation covers it; the test client acknowledges at once and does not decode). GPU pipeline: 36 to 40 frames a second over runs of 15, 20, 30 and 70 s (by ten seconds: 39, 40, 36, 36, 36, 35, 34), about 26 KB a frame, 7.7 Mbit/s, longest gap 101 ms, server CPU 2% of one core, memory unchanged. The server's ladder was at level 0 with a 60 fps cap by the first seconds. After a 20 s stall: the server's memory did not move at the samples (292,048 kB before and after), the first frame came the moment reading resumed (id one past the last: ids count encoded frames, so this says nothing about whether the screen was captured meanwhile, and the first frames may come from the pipe's own buffer, so they need not be fresh), 78 frames in the first two seconds, 37.1 a second over ten. What this shows is memory bounded by the server's combined back pressure (unacknowledged bytes, a blocked writer, a capture that replaces the one pending) and prompt delivery after the stall; it does not show which mechanism, nor that the picture after resuming is current (that needs a timestamp drawn on the screen and decoded after resuming). CPU pipeline (`GLIFF_VIDEO=cpu`): 29 then 40 frames a second, server CPU 139% of one core, memory 197 to 262 MB over 25 s (not followed longer), the same stall result over 15 s (262,028 kB before and after, 85 frames in the first two seconds).
- **Resolved (2026-11-22): about 40 of the 59 frames a second.** The animation's frame clock counted 59.4 ticks a second at every load but the stream carried 36 to 40, also with capture alone (shared memory 38.1 to 39.6 a second in six runs, dmabuf 40.6, PipeWire reporting 0 dropped). Measured next: `gliff-gnome-animate` now also prints how many frames the compositor reported as presented (the frame clock's presentation times, which on Wayland come from the compositor's feedback): 58.6 to 58.7 a second alone, and 59.0 to 59.3 over runs with a capture of the same monitor in the middle, with a median gap of 16.7 ms (the refresh interval) and none without a time (the count of frames that were not yet complete when looked at was 0 too). So the display was never slowed or short of frames; the loss was in the screen cast. In Mutter's source (`meta-screen-cast-stream-src.c`, 50.6) a frame that comes less than `1/max_framerate` after the last one is skipped (lines 1339 to 1350). `pw-dump` during a capture showed the negotiated `maxFramerate` was 60/1: for a monitor Mutter offers 0 to 60 (its default 60, the monitor's refresh rate) and we offered only `framerate` and no `maxFramerate`, so its default stood; the three earlier experiments all varied `framerate`, which is why they changed nothing. Offering 240 was clamped back to 60 by Mutter's range and changed nothing (39.2 and 39.6 fps in two runs). Offering exactly 0, which Mutter's check treats as no limit, gave 59.4 and 59.6 fps in two runs of the same capture. The mechanism (timestamps a little under one refresh interval apart being skipped) is inferred from the source and the numbers; skipped frames were not logged. The change is one property in `gnome-capture`'s format (`pw.rs`), offered for monitor streams only (`Options::unlimited_rate`), and unit tests that every monitor form carries it and no virtual-monitor form does. Sol noted that Mutter 46's monitor offer starts at 1, where a fixed 0 would leave no common value and capture would not start; the code and docs say only 50.6 is tested and no fallback was added.
- **Regression in the first version of this fix, found and fixed the same day.** The first version offered the 0 for every stream, and was pushed. For a virtual monitor Mutter takes the new monitor's refresh rate from the negotiated maximum (`create_mode_info` in `meta-screen-cast-virtual-stream-src.c`), so `--headless` then got a `1920x1080@0.000` mode: on the desktop a capture of it saw 1,306 buffers in 10 s, 1,166 of them with no pixels, while `serve_probe --headless` still passed all its checks, because they only look for sizes and a frame. The probes had not caught this because none of them looked at the monitor's refresh rate; `gliff-gnome-animate` now takes a monitor name to cover (`Meta-` for a private screen) and `serve_probe --headless --load` is allowed, which would have shown the empty buffers as a frame rate.

### Soak: a long session and many sessions on GNOME (2026-11-23)

Until now the longest run was a few minutes. `serve_probe --headless --soak SECS` keeps a real `gliff-server --stdio` session up and resizes it every few seconds through six sizes and scales (1280x720, 1920x1080, 2560x1440 at scale 2, 1600x900, 3840x2160 at scale 2, 1728x972 at 1.5; each size always with the same scale, see the finding below). After every resize it requires a new stream configuration with the size asked for (and the scale asked for: exactly for 1 and 2, between 1 and 2 for 1.5, which Mutter may round) and a frame after it. The server's resident memory, open files and threads are read from `/proc` once per full cycle of the six sizes, so the samples are at the same point of the memory sawtooth (the 4K step costs memory that a smaller one gives back). The first cycle's sample is the baseline; every later sample is held against it on all three counters (memory within 25% plus 50 MB, files within 8, threads within 4), a sample past a margin fails the run, and a run too short for the first cycle and at least one later one (about a minute) fails with "no verdict", since a pass would claim nothing; the growth is judged only on the samples at the end of a full cycle (the final look at `/proc` only checks that the server is still there). The server must also exit with success. A missing, zero or non-numeric duration, or `--soak` without `--headless`, is refused.

These margins are tolerances, not a leak detector: a slow leak under them, or one that needs hours, would pass.

- **Run on the NVIDIA desktop** (GNOME 50.6, packaged `gliff-server`, GPU pipeline, the two real monitors untouched). A first version of the probe (a sample every 15 s, judged only at the end) ran 480 s with 137 resizes, every one with a new stream and a frame (mean 413 ms, slowest 1661 ms); the server's resident memory moved between 287 and 304 MB, open files stayed at 142, threads at 31. The changed probe (per-cycle samples, the checks above), 300 s with 91 resizes, passed: memory 283,964 kB after the first cycle, then 291,300 kB from the second minute to the end (it did not move by more than 4 kB over the last four minutes), open files 142 throughout, threads 30 then 31, 14 samples after the baseline; every resize gave the stream asked for and a frame (mean 167 ms, slowest 225 ms). The mean is lower than the first version's because that one waited for scales Mutter was not going to apply (next point).
- **Finding: a size came back with its first scale (observed, mechanism not established).** The strict check of the stream's scale failed on the first run of the changed probe: after 1920x1080 at scale 1.5, going to 1280x720 and back to 1920x1080 at scale 1 gave scale 1.5 again. In isolation (`gliff-gnome-output-probe revisit`, two runs on the NVIDIA desktop, each reading the scale right after `resize` returned and again two seconds later): 1920x1080 at 1.5 gave 1.5; back at 1920x1080 asked at 1, then 2, then 1 again, it reported 1.5 every time (all four readings, both moments, both runs); 1280x720 asked at 1 gave 1 each time; 2560x1440, not used before, asked at 2, gave 2. The preferred-scale tag was sent on every resize (also for 1.0). What this shows is that, on this desktop and in these runs, a size the monitor had already used at another scale came back with that scale. It does not show how long that lasts (the longest window is about two seconds per reading, within one monitor's life of a minute) or why. Hypotheses, not tested: Mutter remembers a scale per monitor and mode and prefers it to the tag; a fix would then be to ask for a size that differs a little (two pixels) or to make a new monitor. Effect on gliff: the session reads the applied scale back and uses it, so the logical size and the pointer mapping stay right, but a viewer that comes back to a pixel size it had at another scale (a window moved between a 1x and a 2x display, resized to exactly the same pixel size) would get the old scale. A window dragged to an ordinary size is not affected. Not fixed, the case is rare. The soak therefore uses one scale per size.
- **Many sessions:** 25, then 30, then 30 more `serve_probe --headless` sessions in a row all passed, and 30 in mirror mode. `gnome-shell` was watched: its open files went 150 to 172 and then 169 (the extra ones were timer and sync-file descriptors), its memory rose to 696 MB and later fell back by itself (624 MB idle a few minutes on, 482 MB after the mirror sessions, below the 488 MB at the start), and PipeWire's descriptor count stayed at 64. That is recovered memory and no demonstrated persistent growth; it does not prove there is none (the batches were of different sizes, and the memory was not split into what is the shell's own and what is shared).
- **What this does not show:** a run of hours (the longest is 8 minutes, the 300 s one has the cleanest samples), a slow leak under the margins, content that changes (the screen was static, so the frames came from the resizes), a resize to the size and scale the session already has (not run; whether a server answers one with a new configuration is not specified), a client that stalls (the probe always acknowledges), a lost connection in the middle, other GPUs. A defensible leak conclusion needs hours of per-cycle samples (kept with their cycle number), equal batches of sessions with equal idle periods in between, and `gnome-shell`'s memory taken as proportional set size with its descriptors listed by target.
- **Review:** Sol, round 1: eight points, all taken except the no-op resize (stated above as not covered): growth was judged on the last sample only and on memory and files while threads could pass unchecked, "no verdict" counted as a pass, any new configuration followed by any frame passed whatever its geometry, errors in the idle were discarded and a failed exit status passed, a bad duration silently skipped the soak, and the wording above ("settled", "not a leak") went beyond the data.

### Clipboard images and files on GNOME (2026-11-22)

The clipboard bridge was only ever checked with text, and the server's file and image code had never run against Mutter ("Not verified: non-text types, file lists" in the clipboard and wiring entries). `serve_probe --rich-clipboard` now does it end to end, both directions: a plain Mutter client plays the desktop's applications (its own RemoteDesktop session, data per type, none of the bridge's rules) and the probe plays the viewer over the real `gliff-server --stdio`, speaking the clipboard protocol (client request ids odd, chunks of at most 256 KiB, a window of four chunks, acknowledgements).

What the probe asserts:

- **Desktop to viewer:** the desktop copies `image/png` (200 KB), text, and a file list (`text/uri-list` and `x-special/gnome-copied-files`) naming two files (one of 3 MB, twelve chunks) and a folder holding a file. The server's offer must list the image and the text flavours, no file-list type, and exactly the entries `big.bin` (3,000,000 bytes), `note.txt` (28), `pack` (a folder) and `pack/inner.txt` (16), each once. The image, the text and every file are fetched and compared byte for byte. A second copy offering only `x-special/gnome-copied-files` and naming only the note and the folder must give exactly those three entries (that is what a file manager sets first; the first copy had the `text/uri-list` type ahead of it, so only that one was read; the different list keeps a late repeat of the first offer from passing for it).
- **Viewer to desktop:** the probe offers the image, text and the same four entries. The desktop must see `image/png`, the text, `text/uri-list` and `x-special/gnome-copied-files`; pasting the image and the text gives identical bytes; pasting each file-list type makes the server fetch the files into its spool and answer with exactly three paths (`big.bin`, `note.txt`, `pack`), whose contents are compared (the folder must hold `inner.txt`); the `x-special/gnome-copied-files` body starts with `copy`.
- **The server's protocol use:** every chunk it sends must start at the offset received so far and be at most 256 KiB; its requests to the probe must use even ids and name the probe's offer; an acknowledgement may not exceed the bytes sent; an abort or a violation fails the check (also one that arrives just after a paste finished); each fetch and each paste has one absolute 30 s limit, writes and half-sent payloads included, and after an error the probe stops using the stream instead of going on.
- **Not asserted:** the marker type `application/x-gliff-gnome-source` (it is in the printed offer only), the spool's deletion (looked at by hand after the runs: gone), the probe's own chunk window against a slow server.

Result on the NVIDIA desktop (GNOME 50.6, packaged `gliff-server`, GPU pipeline): 3 of 3 runs pass, with no server change, first as a first version and again after Sol's review tightened the checks. The spool and the probe's temp files were gone afterwards.

- **Review:** Sol, round 1: three P1 (an unbounded paste wait; protocol violations that could pass; duplicate or missing entries that could pass), two P2 (temp files leaked on failure; docs beyond the assertions); all taken. Round 2: one P1 (the 30 s limit did not cover writes or half-sent payloads) and three P2 (a repeated offer could pass for the GNOME-only copy; the file list was read after later offers could replace it; an abort after a short answer could pass); all taken. Round 3 (the last): one P1 (the final 500 ms drain could itself hang or swallow a read error; now inside a 5 s limit and a read error fails) and one P2 (after a failed rich check the `--clipboard` text offer reused the stream, and `my_serial` stayed 77; now skipped and cleared); both taken, and these two last edits were checked by `scripts/check.sh` only, not run on the desktop again (it also said `note.txt` is 27 bytes; it is 28: 12 + 1 + 14 + 1, and the run reports 28).
- **Not covered:** a real application's copy or paste (Nautilus, a browser: their own mime types and timing); a consumer that stalls; many concurrent pastes; an abort mid-transfer; items over the 32 MB in-memory cap and files over the size caps; the viewer's own handling (`clipboard_ui.rs`, including its sensitive-selection rule) on GNOME.

### The shortcut prompt on GNOME (2026-11-22)

GNOME Shell asks "Allow inhibiting shortcuts" when the viewer first takes the keyboard (see "M4 part 1 result"). The open question was whether that needs a viewer change (an application id, an upstream edit in `main.rs`). It does not.

- **How Shell decides** (read in the GNOME Shell 50.6 source, `inhibitShortcutsDialog.js`): it saves the answer in the portal permission store (table `gnome`, id `shortcuts-inhibitor`, key the app's desktop id) only when the window maps to a real application; otherwise it shows the dialog every time.
- **Run on the NVIDIA desktop** (GNOME 50.6, the packaged viewer, `gliff.desktop` in `~/.local/share/applications`, the window given focus by an injected click, the dialog answered Allow by injected keys). Started from ssh as plain `gliff`, with the desktop file installed: the dialog came, Allow worked for that run, nothing was saved (the table stayed empty) and the next launch asked again. Same, with an application id added in a scratch copy of the viewer: also not saved. Started through the desktop file with `gio launch`: the answer was saved (`gliff.desktop: GRANTED`, for the unmodified viewer, no application id) and the next launch took the shortcuts at once (`inhibited=true`, 11 ms after focus, no dialog). With a scratch viewer that has the application id `org.gliff.Gliff`, launched through a desktop file of that name, the same: saved and remembered.
- **So:** launching from the application grid (or `gio launch`) is what makes GNOME remember; a terminal or ssh launch of plain `gliff` still asks every time. I did not test why Shell does not match a window of a process it did not launch, only that it does not. No upstream file is touched; `nix/package.nix` now also names GNOME in the desktop entry's comment and keywords (the file itself is upstream's `pkgbuild/gliff.desktop`).
- **Test caveat found on the way:** running the viewer and a server on the same desktop shares one clipboard, and the bridge looped for four minutes (4,572 requests, one "Pasting text" notification each) until killed. In real use the two sit on different machines. Use `--no-clipboard` on the viewer for a one-machine test. Whether the server's own paste raises such a notification on a GNOME host in normal use was not checked, and the notification's source was not found (not in Shell's JavaScript, not in Mutter's libraries). The loop has no brake in the clipboard code; not looked at.
- **Not covered:** other GNOME versions, a GNOME that has Boxes or other apps' answers (the permission table was empty on the desktop before and after: my entries were deleted, leaving an empty `shortcuts-inhibitor` id), launching from the real application grid by hand (`gio launch` stood in), whether the packaged `Exec=gliff` resolves in a NixOS profile (the test used absolute paths).
- The desktop run was by hand and is not repeatable by a script. The packaging edit is checked by building the package and reading the installed entry (below).

### Upstream sync: how much the fork costs to keep (2026-11-21)

Asked: do the changes so far still let us merge upstream as it changes? Answer: yes, but not for free. Everything GNOME is in new crates and files that upstream cannot conflict with; the cost is the seam in `crates/gliff-server/src/session.rs`.

- **Footprint** (`git diff` from the merge base `9d93732`, which is also upstream's tip, so no real merge has been tried yet): `session.rs` 46 hunks (+75, -103), `clipboard.rs` 4, `hypr-capture/src/lib.rs` 6, `main.rs` 2, `gliff-vk/src/device.rs` 1 (one new function), the workspace and server manifests, `action.yml` one line, `README.md` a short note, and the generated `Cargo.lock` (regenerate it after a merge, do not hand-merge it).
- **Upstream churn before the base** (the project is two months old, 325 commits): `session.rs` was touched by 24 commits in the last 30 days (53 in all), `main.rs` 11, `hypr-capture/src/lib.rs` 21, `gliff-vk/src/device.rs` 11, `clipboard.rs` 6.
- **Proxy test** (throwaway clone, deleted): our diff applied with a three-way merge onto upstream 10, 20, 40 and 60 commits before its tip conflicts in `session.rs` in 7, 9, 16 and 21 regions, and from 40 commits back also in `hypr-capture/src/lib.rs` (4); at 60 one region each in `main.rs`, `device.rs` and `action.yml`. This shows where upstream has been editing, not how often a forward merge will conflict (it applies a newer diff to an older tree). Expect hand-resolved conflicts in `session.rs` at most syncs; the more often we sync, the smaller each one.
- **Clean merges can still break GNOME** (Sol, round 1): a new direct compositor call in `session.rs` or any new server file; a changed type that the `gnome-*` crates share with `hypr-*` (signatures fail to compile, but changed defaults, event order, coordinates, buffer ownership and fallbacks compile and run wrongly); our `FrameSource` in `hypr-capture/src/external.rs` depends on private capture-thread commands; a new protocol message the backend must act on. `gliff-probe` uses `hypr_*` too.
- **Changes made for this** (Sol's recommendations 1 and 3): the "needs GNOME mirror" check in `scripts/sync-upstream.sh` now covers whole crates (`hypr-*`, `gliff-server`, `gliff`, `gliff-probe`, `gliff-proto`, `gliff-vk`) and the workspace manifests, not a list of file names; and a sync pull request that carries the label stays a draft after green tests, with a comment asking for a check on a GNOME session first (before, passing tests took it out of draft). Not done: running the sync daily instead of weekly, and a first manual run of the workflow (it has still never run; it needs the repository setting named in "M6 result"); both are the owner's call. Not done on purpose: shrinking the `session.rs` diff further (Sol: only incidental churn is worth removing, and a larger abstraction would cost more than it saves).
- **Merge checklist** for a sync pull request: regenerate `Cargo.lock`; resolve `session.rs` by keeping upstream's behaviour and routing any new compositor call through `Backend`; run `scripts/check.sh`; run the GNOME probes if the PR carries the label.

## Rule: keep upstream files in sync-able shape

This fork merges omacom's `main` regularly, so our features must not make that merge harder.

- New code goes in new crates and new files (`gliff-backend`, `gnome-*`, `hypr_backend.rs`, `backend.rs`, `nix/`, `flake.nix`, `docs/gnome-backend.md`).
- An upstream-owned file is edited only when there is no other way, with the smallest change that works (one line where possible). No reformatting, renaming or tidying of upstream code. Upstream docs (`docs/architecture.md`, ...) are not edited, and `README.md` only by the short note listed below; GNOME documentation goes in `docs/gnome-backend.md`.
- Every upstream-owned file we edit is listed here with the reason. A new entry needs a reason too.
- `Cargo.lock` is generated: after a merge, regenerate it instead of hand-merging.
- To see the footprint at any time: `git diff --name-status upstream/main` (`M` rows are upstream files we changed).
